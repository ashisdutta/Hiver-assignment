# Decision Log

Chronological record of the non-obvious calls made while building the preprocessing pipeline, the agent, and the eval harness. Each entry states the decision and the actual reason it was made, not just what was done.

- **Split `grounding_pool` / `eval_pool` by partitioning, not independent sampling, to make leakage structurally impossible.** The subsample's thread-id list is shuffled once (fixed seed) and cut into two contiguous, non-overlapping slices — `eval_pool` gets the first 20%, `grounding_pool` the rest. Because it's a single list cut in two, no thread_id can appear in both pools by construction (asserted in code, not just assumed). Exact-duplicate dedup also happens *before* the split, so duplicate `(customer_message, reply)` pairs can't land in both pools either. This directly targets the brief's concern: if an eval example's exact resolution is also sitting in the retrieval index, reply-quality scores get inflated by memorization instead of testing real generalization. Final split: 3,193 grounding_pool threads / 797 eval_pool threads.

- **Keep all triage ("please DM us") replies and tag them (`is_triage`) rather than filter them out or ignore the distinction.** Filtering would have shrunk the corpus significantly (most real AmazonHelp replies are triage-style) and removed legitimate "escalate to DM" examples the routing stage needs to learn from. Tagging preserves full data volume while letting every downstream stage (grounding retrieval, golden-set sampling, routing eval) filter or stratify on the flag later without re-running preprocessing. Confirmed with the user explicitly rather than decided silently, per the brief's requirement to document this tradeoff.

- **Iterated the `is_triage` regex through several rounds of sample-driven review instead of trusting the first pass.** Initial heuristic tagged only 8,830/152k replies True; visual review of sampled `False`-tagged rows found systematic misses (link-redirects phrased without the initial keyword list, e.g. "you can do so here:", "kindly reach out to our support team here:"). Expanded the patterns twice based on concrete failing examples, landing at 29,659/152,099 tagged True. Stopped when a fresh sample kept surfacing new open-ended phrasing variants (whack-a-mole territory) — deliberately accepted as a coarse heuristic for downstream stratification, not ground truth, rather than chasing diminishing returns.

- **Fixed a text-cleaning bug where stripping URLs left orphaned punctuation, corrupting sentences.** A user-reported pattern check found replies trailing off mid-sentence ("...recover the parcel:") or two clauses smashed together around a bare colon ("Please fill this form: and I'll contact you soon."). Root cause: the URL regex's greedy `\S+` match swallowed trailing sentence punctuation attached to the link. First fix attempt (a lookahead stopping before punctuation) broke on shortened domains like `t.co`, whose internal periods look identical to a trailing sentence period. Final fix: match the URL/phone greedily as before, then trim trailing punctuation off the *matched string itself* in a callback and re-insert it into the output — preserving the sentence's real punctuation instead of deleting it with the link.

- **Fixed a language-detection bug that let code-switched threads pass the English-only filter.** Original implementation concatenated all of a thread's brand-reply turns before running language detection once per thread — an English-majority thread with one non-English turn (e.g. thread 338562, which switches to Spanish mid-conversation: "Comprendo. Por favor, verifica este enlace") still classified as `'en'` on the combined blob. Fixed to per-turn detection, dropping a thread if any single brand turn is confidently non-English (short replies too brief to classify don't block the thread, to avoid false-dropping things like "Thanks!").

- **Dropped confidence-threshold routing in favor of intent rules + grounding strength.** `classify_intent`'s confidence scores were uniformly high (0.92–0.97) even on a borderline/ambiguous test case, showing the model wasn't expressing calibrated uncertainty — a confidence threshold would have been noise, not signal. Routing (Stage 4) instead uses two signals that actually discriminate: hard intent rules (`billing_dispute` → escalate, for financial risk) and `retrieve_grounding`'s no-strong-match flag (unreliable draft → escalate).

- **Isolated the project in a dedicated `.venv` after `sentence-transformers` broke the shared global environment.** Installing it pulled a newer `transformers` (4.30.2 → 5.17.0) that conflicted with `torchvision`/`huggingface-hub` versions other unrelated tools in the user's global anaconda environment depended on (`simpletransformers`, `datasets`, `tensorflow`). Reverted `transformers` to restore the global environment, then created an isolated `.venv` for all project dependencies going forward — zero further risk to the shared environment, and matches the brief's "pip install -r requirements.txt" reproducibility expectation anyway.

- **Skipped intent-prefiltered retrieval in `retrieve_grounding`, using plain semantic search over the whole pool instead.** The brief's Section 3 design calls for pre-filtering by predicted intent before ranking by similarity (to avoid cross-intent false matches). Dropped for v1 specifically to avoid burning Groq's free-tier rate limit (30 req/min, 1,000/day) on a second classification pass per query, given the project's time constraints. Documented explicitly as a v1 simplification, not a silent omission — a future pass could add it back now that the taxonomy and classifier are validated.

- **Reduced the golden set's scope in three separate, documented steps rather than running everything at full size.** 150 rows labeled (of `eval_pool`'s 797, per the brief's 150–250 target) for intent/routing metrics — cheap, no reply generation needed. Only a 30-row random subset (seed=42) of those 150 got real `draft_reply` + baseline replies + LLM-judge scoring (Part 2), since that step is Groq-call-heavy (120 calls) and time-constrained. Only a 15-row subset of *those* 30 got manually hand-scored for judge validation, since that requires the user's own time. Each reduction is stated as an explicit scope decision at the point it's made, not silently absorbed into "the eval."

- **Used Claude (this assistant) directly for golden-set labeling instead of wiring up a new Anthropic API integration.** Initially started setting up `ANTHROPIC_API_KEY` + SDK for a "best model" labeling pass; the user redirected to having the assistant label all 150 rows directly through its own reasoning in-session, avoiding new credential setup entirely. Labels were produced independently per row (full untruncated context pulled from `eval_pool.jsonl`, not just the worksheet's truncated snippets) rather than copying the pipeline's `suggested_intent`/`suggested_route` — verified by `run_eval.py`'s hard rubber-stamp check (errors out if true/suggested agreement exceeds 90%); actual agreement landed at 89%/89%, with genuine, individually-justified disagreements (e.g. reclassifying fulfillment errors like "wrong item shipped" out of `delivery_issue`, since taxonomy-wise they're not really a transit problem).

- **Switched provider mid-build: Anthropic (default agent-building assumption) → Groq (`openai/gpt-oss-120b`), then absorbed a mid-project model deprecation and two rate-limit-driven key swaps.** User specified Groq from the start (OpenAI-compatible API, `python-dotenv` + `.env`/`.env.example` pattern, key never committed) because `llama-3.3-70b-versatile` — Groq's previous recommended production model — was deprecated 2026-08-16, making `gpt-oss-120b` the current pick. Mid-eval, a run hit Groq's daily token cap (200,000 TPD, exhausted at 199,224 used) partway through `eval_replies.py`; since results weren't checkpointed yet, the whole run's output was lost. Fixed by adding incremental persistence (draft-reply cache + per-row result writes, resumable on re-run) and having the user swap in a fresh Groq API key to finish. Net effect: the pipeline's LLM dependency survived a provider-level constraint change and two live credential swaps without any code redesign, only config/robustness additions — worth calling out as an operational resilience property, not just a one-off fix.

- **Designed one canonical `(thread_history, customer_message, reference_reply)` example per thread using the *last* brand reply, not every reply.** Needed to satisfy two schemas at once: the live agent's input format (`thread_history` + current `customer_message`) and the golden set's fields (`customer_message`, `reference_reply`). Took the thread's final brand-authored turn as `reference_reply`, the customer turn immediately preceding it as `customer_message`, and everything earlier as `thread_history` — giving exactly one well-formed, schema-compliant example per thread rather than needing per-turn fragmentation.

- **Added an empty-text safety filter after `@mention`/URL stripping produced blank `customer_message`/`reference_reply` values.** Tweets that were only an `@handle` + a URL (e.g. screenshot-only replies) cleaned down to an empty string, which would have produced useless (empty-query) grounding/eval examples. Fixed by preferring the last *non-empty* customer turn as `customer_message` and dropping threads entirely only when no valid non-empty turn exists (5–10 threads out of ~4,000, not a meaningful sample-size hit).

- **Tightened `draft_reply`'s prompt twice after finding concrete fabrication failures in testing, not from a hypothetical risk.** First: the model claimed "we've escalated this to our technical team" with nothing in the conversation or grounding examples supporting that an internal action had actually been taken — fixed by explicitly forbidding claims of already-taken internal action unless shown in context. Second (caught during full-pipeline stress testing, not the first isolated test — `temperature=0.3` made it stochastic): the model hallucinated a plausible-looking but fake Amazon help-center URL. Fixed using a structural fact rather than a fragile keyword ban: since preprocessing strips every URL out of `clean_text`, no grounding example or thread-history turn *can* legitimately contain a real URL — so the prompt just forbids the model from ever writing one out, with no exceptions to reason about. Verified with a 6x repeated stress test on the exact failing case post-fix (0 recurrences).

- **Reused each `sample_rows.py`/worksheet's already-computed `suggested_intent` as `draft_reply`'s intent input in Part 2, instead of re-running `classify_intent`.** Saves 30 redundant Groq calls, and more importantly mirrors actual production behavior — the live pipeline would feed its own (imperfect) intent prediction into reply drafting, not an oracle label, so scoring `draft_reply` against ground-truth intent would have overstated real-world reply quality.
